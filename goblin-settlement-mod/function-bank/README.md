# 独立函数任务库

用途：把边界清楚、无需游戏状态的计算交给其他模型；交付代码经过验收后，在相应模块开发时接入。当前只准备任务规格，没有声称函数已实现或已可用于游戏。

## 使用方法

1. 从下表选择一张任务卡，把整个文件发给另一个模型即可；不需要发送完整游戏计划和聊天历史。
2. 让它交付 Java 源文件、独立验证文件和 NOTES.md。能访问本项目时写入对应 submissions 子目录；否则用户将输出保存到该目录。
3. 提交后状态仍是“待验收”。主开发者检查规则、接口、边界、许可证/来源及验证内容，自己运行验证；不能仅凭提交者说通过就接受。
4. 验收通过，将该修订的源文件、验证和记录复制到 accepted/任务编号/修订号，并登记验收证据。修订有变化就重新验收。
5. 开发对应模块时按登记表找到候选成果，接入运行时源码并验证游戏调用。登记接入路径。此后维护运行时那一份，accepted 中的旧副本只是历史快照，不是第二个需要同步维护的实现。

## 成本与接口约定

- 首批只做以上三张卡。它们可让用户手头的较便宜模型尝试；不把模型品牌当作质量保证，按结果验收。
- 一张卡应足够独立，又有实际复用价值。普通加减法直接使用 Java 运算，不为了分工另造一层函数。
- 先写清输入、输出、单位、异常、边界和例子，再安排实现；不要先大量囤积用途不清楚的函数。
- 计算只用 Java 21 标准库，不调用 Minecraft、Fabric、网络、文件、当前时间、随机数或全局可变状态，不修改输入。
- 卡片的函数签名是本次交付契约；数学行为验证后尽量保持稳定。未来适配 Minecraft 的坐标、物品和存档类型，在调用层转换。
- 需求真的改变时升级任务版本，并更新验收案例；不要随手修改含义后继续沿用旧验收结论。
- 函数验证通过只表示输入输出契约成立。区块是否活动、玩家是否允许施工、库存是否已被拿走等必须由游戏集成层重新判断。

## 不提前拆成普通小函数外包的部分

实际扣料与预留提交、出生名额登记、实体死亡与卸载、任务中断恢复、存档迁移、桥梁安全和世界修改权限，需要结合真实状态设计与验证。可以外包其中明确的纯计算片段，但主程序负责把整个过程正确地串起来。

本目录位于 src 之外，当前 Gradle 不会自动将 submissions/accepted 中的 Java 文件打进模组。
