# 哥布林自治聚落：实现技术方案

记录日期：2026-09-24  
状态：架构设计基线；工程骨架与部分纯计算已建立，实际进展见 [CURRENT_STATUS.md](CURRENT_STATUS.md)。下文设计不表示所有功能已经实现。

## 1. 工程与发布单位

推荐：**一个独立的 Fabric 模组、一个 Gradle 工程、一个最终安装用的 JAR；内部按职责划分代码。** 项目与现有 `ai-chat-mod` 分开，使用独立的模组 ID 与版本号。将来某部分获得独立用途且接口稳定时，才评估拆成独立库或附属模组。

目标环境记录为 Minecraft Java 1.21.11、Fabric Loader 0.19.2。建项时核对并固定相容的 Java、Loom、Fabric API 与映射版本，禁止同一阶段的 AI 任务使用不同 Minecraft 版本的示例。开发与试玩使用独立测试世界，验证完成后再安装到常用环境。

Fabric 支持把客户端显示代码与通用代码分成不同源码集合，最终仍打包为一个模组 JAR；服务端权威管理出生、箱子、施工和关系，客户端显示模型、动画、界面与规划预览。游戏中的自治行为由本地规则和任务调度驱动，不调用云端大模型。

参考：[Fabric 1.21.11 项目结构](https://docs.fabricmc.net/1.21.11/develop/getting-started/project-structure)、[Fabric Loom 与客户端源码划分](https://docs.fabricmc.net/1.21.11/develop/loom/)。

## 2. 内部职责边界

以下名称表示同一个工程里的代码包和服务，初期不各自建立 Gradle 子项目。

| 部分 | 维护的状态或行为 | 边界 |
| --- | --- | --- |
| `colony` | 聚落身份、人口名册、孕育名额、发展需求、任务协调 | 不保存另一份箱子真实库存 |
| `citizen` | 居民实体、动作、背包、作息、任务执行 | 不自行决定全镇人口或土地上限 |
| `economy` | 实际库存查询、预留、运输、生产与工具更换 | 不直接选建筑地块 |
| `planning` | 地形、领地、道路、桥梁与建筑方案 | 只提出方案，不直接修改世界 |
| `construction` | 工地、分步施工、材料消耗、维修和恢复 | 不擅自扩大领地 |
| `defense` | 傀儡、警报、巡逻、战斗、维修需求 | 不自行改动玩家宅地规则 |
| `interaction` | 玩家地块、通行与使用权限、交易、偷窃与关系 | 不绕过实际库存发物品 |
| `platform` | Fabric 注册、游戏生命周期、存档、网络同步 | 尽量不包含玩法决策 |
| `client` | 模型、动画、公告牌和规划预览 | 不决定出生、扣料或施工 |

每类关键数据只有一个权威来源：人口名册由 `colony` 维护；实际物品由箱子、居民背包和世界中的物品承载；经济账本只记录索引与预留；工程进度由 `construction` 管理；能否改动地块由 `interaction` 的权限服务判断。其他部分通过明确请求读取或提交，不各自复制一套可变状态。

接口优先设在真实跨界处，例如库存、世界改动、地块权限与保存。简单规则可以写成独立计算函数。协调器安排任务顺序，具体采矿、找路、扣料、施工各由对应部分完成，避免出现一个包办所有内容的巨大类。查询使用明确返回值；“房屋完工”“桥梁损坏”等已发生的事实可以发布通知。关键资源与权限流程不靠无序广播串联。

## 3. 典型运行流程

住房不足 → 聚落提出需求 → 规划检查地形与领地、生成蓝图 → 权限服务批准位置 → 经济服务检查并预留材料 → 建造服务建立持久工地 → 居民领取搬运或施工任务 → 实际移交物资并放置方块 → 工地验收 → 登记可用住房 → 人口系统重新评估繁衍。

每个阶段都有结果和失败原因：保护区、材料不足、路径不可达、地形不符、区块未活动、工具损坏、居民死亡等。失败后暂停或重新规划，不重复执行已有成果。

道路、桥梁和房屋共用“方案 → 权限与材料核验 → 工地 → 分步执行 → 验收”的骨架；路线选择、桥梁安全和房屋蓝图是各自的专门规则。

## 4. 持久化与中断恢复

每个聚落使用稳定 ID；居民、家庭、仓库、工程和任务引用 ID，不仅依赖临时实体对象。需要保存居民出生与年龄、人口预占、家族关系、职业、实际背包、聚落边界、地块权限、工程阶段、预留材料、桥梁禁行、傀儡归属与玩家关系。保存数据带版本号，以便未来修改结构。

任务按待领取、执行、等待、完成、取消等状态推进。已实际搬走的物品以居民背包或工地库存为准；尚未实际领取的预留可在取消后释放。卸载时暂停，重载时检查真实箱子、地形和实体状态后恢复。重复加载不重复出生、不复制物品、不重复放置或扣除方块。

首次实现前核对目标版本的 [Fabric Saved Data](https://docs.fabricmc.net/1.21.11/develop/saved-data) 与 [Data Attachments](https://docs.fabricmc.net/1.21.11/develop/data-attachments) 文档，再选择各类数据的保存位置。存档一致性需要实际重载测试，不仅凭读写函数通过编译判断。

## 5. 世界修改、加载边界与性能

采矿、伐木、耕种、道路、桥梁、房屋等每次世界改动都经过同一个权限入口，规划阶段检查一次，真正放置或拆除时再次检查。所有库存和方块写入由服务端执行，玩家发出的客户端操作只是请求。

聚落活动受实际区块模拟约束。核心聚落不活动时暂停全镇任务；边缘区块不活动时，相关箱子、工地与居民仍保留身份，但任务不可把它们当作可访问对象。规划可以保留意图，回到活动区域后重新核验现场。默认不为城镇强制加载区块。

先使用有限范围与固定频率的规划：限制每次地形检查的地块数、同时开工项目、失败重试频率和道路重新计算范围；已有道路结果在地形或权限改变时失效。先测量瓶颈，再考虑后台计算；任何后台方案只能分析不可变快照，实际世界与库存改动仍返回服务端执行并重新验证。

## 6. 内容数据与校验

建筑蓝图、材料清单、房屋升级关系、傀儡参数、职业倾向、名字、对话与可调平衡数值尽量放在受校验的数据文件中。核心任务调度、真实库存交换、权限判定与存档恢复仍由代码实现。

格式要检验：资源标识是否存在、配方和升级链是否成环、蓝图是否有合法入口、桥梁方案是否满足安全尺寸、配置数值是否越界。先实现一套建筑流程并验证，再扩展多种蓝图；自定义傀儡复用通用守卫逻辑，通过数据表现级别差异，原版铁傀儡使用专门接入层。当前只设计哥布林，不提前构造庞大的多种族通用框架。

## 7. 分阶段开发和验收

| 顺序 | 技术交付 | 验收证据 |
| --- | --- | --- |
| 1 | 独立工程、固定依赖、模组启动、最小存档与权限入口 | 测试世界正常启动，重载状态一致 |
| 2 | 一个居民从真实箱子取料、搬运、完成一小段建筑 | 看得见真实物品移动，扣料与施工一致 |
| 3 | 多居民共享任务、库存与工地，处理偷料、死亡、取消和重载 | 无重复资源和重复施工，失败可恢复 |
| 4 | 农业、工具、家庭、人口额度与领地 | 自给生活，孩子成年前不增加土地额度，出生不超限 |
| 5 | 道路、桥梁、地形判断与玩家宅地 | 安全通行，缺料停工，保护区冲突改线 |
| 6 | 房屋升级、六级傀儡、关系与更多蓝图 | 各升级链材料可达，窃取和补偿有真实反馈 |
| 7 | 成熟聚落性能、异常恢复、资源与美术整理 | 长时间运行、重载和复杂地形验证通过 |

在早期用小场景专门验证“桥梁安全施工”和“保存后任务恢复”，及时暴露架构问题。每一阶段保持可运行版本。对人口公式、额度和材料计算使用快速单元测试；箱子、世界改动、实体与重载使用 Minecraft GameTest 和实际试玩场景。[Fabric 1.21.11 自动测试文档](https://docs.fabricmc.net/1.21.11/develop/automatic-testing)

## 8. AI 模型与成本分配

默认开发设置：**GPT-6 Sol + Medium**。按任务难度临时调整，而不是整个项目保持最高模型、最高推理。以下是推荐分工，具体效果以实际验收为准。

| 任务 | 首选 |
| --- | --- |
| 文案、翻译、名字、已有格式的配置和资产清单 | Luna Low |
| 按合格模板补充配方、房屋蓝图、傀儡参数 | Luna Low 或 Medium |
| 边界清楚的公式、小范围修改及其独立验证 | Luna Medium |
| 常规实体行为、显示接入和日常功能 | Sol Medium |
| 库存预留、任务恢复、施工顺序、路径和跨区块一致性 | Sol High |
| 首次架构审查、跨系统不变量、严重疑难故障 | Astra High，必要时提高推理 |

模型选择看任务范围和错误影响，而不是仅看模块名字。人口公式本身可交给 Luna；出生、死亡、保存和多个聚落的共同约束由 Sol 或更强模型审查。遇到同一错误连续两轮修复无进展，先收集复现和证据，再提高模型档位。

DeepSeek、Kimi 可以在能够读取工程并执行验证的外部开发工具中承担格式清晰、独立算法、配置补充和独立审查。先用相同的三个代表性任务比较：新增建筑配置、人口边界计算、修复可复现的任务中断。记录最终通过验收的费用、重试次数与人工返工，再决定长期分工；不能只根据品牌或一次调用价格判断。

OpenAI 官方 [模型选择](https://developers.openai.com/api/docs/guides/model-selection)、[模型价格](https://developers.openai.com/api/docs/models/compare)、[推理强度](https://developers.openai.com/api/docs/guides/reasoning) 页面是目前模型建议的依据。API 每百万 token 标价不能直接换算 Codex 订阅额度，且输出推理、重试与上下文都会影响实际任务成本。

## 9. 低成本协作流程

接续入口是 [CURRENT_STATUS.md](CURRENT_STATUS.md)；独立计算的第一批可直接发送任务卡见 [函数任务库](../goblin-settlement-mod/function-bank/README.md)。卡片自带完整输入输出、边界、验收与提交位置，其他模型不需要读取整个项目历史。候选代码先提交、再验收、最后接入；游戏类型转换放在调用层，避免反复改动已验收的计算规则。

任务卡至少写清目标、输入、输出、允许修改范围、不可违反的规则、验收方法。大任务先拆成可单独验证的步骤，例如路线生成 → 材料计算 → 施工任务 → 中断恢复 → 完工登记。较便宜的模型优先处理接口已固定的步骤。

保持一个集成负责人，负责核对接口、运行相应验证和合并结果。能够独立修改的内容可并行；共享人口名册、库存或存档结构时先确定唯一负责人。多个模型同时开发使用独立分支或工作目录。项目文档只保留玩法决定、技术边界、当前任务与开发约定，任务只加载相关上下文，避免每次反复读完整历史。

最终衡量指标是**完成并通过验收的任务成本**，包含模型调用、重试、审查和人工修复。
