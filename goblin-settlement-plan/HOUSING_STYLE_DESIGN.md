# 住宅风格（更多蓝图）设计

更新日期：2026-09-27。依据：TECH_DESIGN.md 第 6 节「先实现一套建筑流程并验证，再扩展多种蓝图」；HOUSING_DESIGN.md §10「更多蓝图：`Home.variant` 仍是朝向镜像，不是可选形制」；HOUSING_BLUEPRINT_DESIGN.md（数据文件与四条校验）。

## 1. 目标与范围

**目标**：让住宅数据文件能容纳**多种形制**，从而兑现第 44/45 轮数据化能力的用途——目前能力已就位，但真实数据只有一种形状、一种材质。

**本轮做**：
- 数据模型引入**风格**维度（一套风格 = 一整套五级链）。
- `Home` 记住用了哪套风格；旧存档兼容。
- 选择规则：确定性偏好 + 放得下兜底。
- 校验器逐套执行既有四条规则，外加外层规则。
- **由开发方起草 2 套新形制**（连同现有 cottage 共 3 套），端到端跑通。

**本轮不做**：玩家自定义蓝图、数据包重载、形制的美术资源；通用施工路径的材料泛化。

## 2. 为什么单位是"整栋风格"而不是"每级多套"

各级是**累加**的：建到容量 2 级 = 1 级全部方块 + 2 级新增方块（`steps()` 直接拼接各级步骤列表）。若允许"每级多套形制"，则 1 级的第 B 套必须与 2 级的第 C 套逐级接缝，组合数为各级套数之积，且**没有任何简单规则能保证接缝**——两套几何的墙可能差一格，接起来就是破屋。

**整栋风格**天然自洽：一栋房子从注册起就定下一套完整五级链，升级必然在同一套几何里进行。

## 3. 数据模型

`BlueprintSet` 由「一条 capacity 链 + 一条 quality 链」改为「一组风格」：

```java
public record Style(String id, List<Stage> capacity, List<Stage> quality) { }
public record BlueprintSet(List<Style> styles, int reserveBasic, int reserveExpanded) { }
```

（`Stage` 与 `HousingRules.Step` 不变。）

数据文件格式随之换代。mod 未发布、文件随 jar 打包，因此**直接硬切**，不保留兼容读法；文件由生成脚本重新产出。

```json
{
  "reserve_basic": 8,
  "reserve_expanded": 24,
  "styles": [
    { "id": "cottage",    "capacity": [ ... ], "quality": [ ... ] },
    { "id": "lean_to",    "capacity": [ ... ], "quality": [ ... ] },
    { "id": "side_porch", "capacity": [ ... ], "quality": [ ... ] }
  ]
}
```

**旧存档兼容**：`Home` 新增可选字段 `style`（`optionalFieldOf("style", 0)`）。旧存档只记了镜像号（JSON 字段名 `blueprint`），加载后风格一律落到下标 0。**下标 0 必须是现有 cottage**，这样已建成的房子在新版本里几何一字不变。

## 4. 校验

逐套执行 HOUSING_BLUEPRINT_DESIGN §4 的四条（资源标识存在、升级链无环、蓝图有合法入口、数值不越界），外层再加：

- 至少一套风格（否则聚落永远建不了房子）；
- 风格 `id` 唯一且非空；
- 每套风格仍必须有 `MAX_CAPACITY_TARGET + 1` 个容量级、`MAX_QUALITY_TARGET` 个品质级（阶梯长度本轮仍是代码常量，理由同第 44 轮）。

入口校验按**每套自己的链**分别做（容量链、品质链各一次），与现状一致。

## 5. 选择规则

**确定性偏好 + 放得下兜底**：

1. `preferredStyle(level, styleCount) = floorMod(level.getX() * 31 + level.getZ() * 17, styleCount)`——用锚点床的坐标算，**显式算式，不依赖 `BlockPos.hashCode()` 的契约**（`hashCode` 无跨版本保证）。
2. 注册一栋新房子时，试的顺序是「首选风格 → 其余按数据顺序」，每个风格内再试镜像 0/1/2（**镜像机制与今天完全一致，一行不改**）。
3. 第一个通过 `siteSuitable` 的（风格, 镜像）组合被写入 `Home`。
4. 全部组合都不合适 → 该地块不注册房子，与今天"三个镜像都不合适"时的行为一致。

这样同一聚落内的房子长相有变化，且**同一存档每次加载、每次重启都得到同样的结果**（哈希只依赖床的坐标），同时地形保留否决权。

## 6. 接线

- `HousingBlueprints` 按风格解析并缓存全部步骤（仍是 `ResolvedStep(Block, Item)`）；暴露 `stages(styleIndex)` 与 `steps(styleIndex, capacityTarget, qualityTarget)`。
- `HousingCoordinator` 的 `nextSite` / `stepAt` / `assignedStep` / `stageFullyBuilt` / `siteSuitable` / 领料闸 / 仓库选取都从传入的 `home` 取风格下标。
- `Home` 的 codec 加 `style` 字段与范围校验（`0 <= style < 风格数` 无法在纯 record 里校验，因为 record 不知道数据文件——**越界在读取时钳到 0** 并在日志里说明，与 `HousingBlueprints` 不可用时停摆同一策略）。

## 7. 三套形制

精确偏移由 `tools/generate_housing_blueprints.py` 产出（第 44 轮的惯例：设计文档定意图，脚本持数字，校验器与检查负责证伪）。三套都必须满足：落在校验盒（`|x| <= 3`、`0 <= y <= 4`、`|z| <= 2`）内、通过入口洪水填充、**级内**坐标不重复、**同一格被多级投放时必须声明同一种方块**。

**关于"跨级重复"的更正**（2026-09-27，实现时由校验器抓到）：本节早先写的是"级与级之间不重复投放同一格"，**那是错的**。cottage 本身就是反例——它的棚顶（y=3）在容量 0 级与 1 级都会被覆盖，这正是既有几何的写法，而 `nextSite` 遇到"已经是该方块"的格会直接跳过，所以重复投放本身无害且被允许。

真正需要守的是**同格同料**：若某一格被两级投放却声明了不同方块，先跑的那一级会把格子占住，后一级的步骤永远等不到空气格，表现为工人反复 `waitReason` 卡死。因此校验器检查的是"同一格的方块在所有级里一致"，不是"格不重复"。

- **`cottage`**：**现状那套逐字保留**。三个容量级步数必须是 21 / 71 / 10，累计 21 / 92 / 102——这是"已建成的房子零行为变化"的证据。
- **`lean_to`**（单坡棚，紧凑）：更窄的落地范围（3 格宽 × 5 格深，而非 cottage 的 5×5），顶盖更低更平；容量 1 起在 **-z 侧**留两格门洞（cottage 的门开在 +z，形制之间连开口方向都不同）；容量 2 补一段矮墙围合。品质级为低矮的压顶梁。
- **`side_porch`**（带侧廊）：主体沿用 cottage 的 5×5，但在 **x=3 一侧**从容量 0 起就带一条有柱的侧廊，容量 2 给侧廊加顶。品质级为侧廊上的立柱饰。

**三套的容量轴都必须是 3 级、品质轴 2 级**，因为 `builtCapacity(0/1/2)` 与 `canGainCapacity` 把"能住几人"绑定在级数上；不同形制改变的是**外观与占地**，不是**能住几人**。

## 8. 验证方式

- `BlueprintCheck` 增：三套风格各自的四条校验；风格 id 唯一；至少一套；`preferredStyle` 的确定性与覆盖区间（同坐标恒同结果、不同坐标能覆盖到多个下标）；旧档 `style` 缺省落到 0。
- 生成脚本打印每套每级的步数。**cottage 的三个数必须仍是 21 / 71 / 10**，否则就是现有几何被动过。
- 既有 12 项独立检查全部保持通过；完整离线构建。**不做游戏内验证**（按用户约定）。

## 9. 风险

- **新形制由开发方起草**：`lean_to` 与 `side_porch` 的形状、尺寸、观感是开发方的设计，不一定符合用户审美；用户已表示可以改。它们在游戏里好不好看、好不好住，**只有统一测试时才能判断**。
- **`siteSuitable` 的成本随风格数线性增长**：它现在要遍历全部阶段的全部步骤，注册时还要 ×3 镜像。3 套风格下是可接受的；风格数大幅增长时需要重新设计（例如先用包围盒粗筛）。
- **床位绑定半径是全局常量**：`HousingRules.BIND_RADIUS = 8`、床位互斥区 4 格对三套形制一视同仁。`lean_to` 占地更小，8 格半径相对偏大，可能出现"房子比绑定范围小"的浪费——不影响正确性，但意味着紧凑形制在密集布局下未必更省地。
- **旧档钳制策略会掩盖越界**：风格下标越界被钳到 0 而不是报错。这避免了一存档打不开，但意味着**数据文件删掉某套风格后，存档里用它建成的房子会静默变成 cottage 的几何**，进度推导随之改变（HOUSING_DESIGN §10「进度推导的正确性」同类风险）。必须在状态文档里写明：**删风格是不安全的操作**。
- **新形制推高了格子数**：`siteSuitable` 里"地面必须坚固"的检查对每个 y=0 步骤都要做。侧廊与更宽的形制会增加 y=0 步骤数，从而收紧可选地块（可能需要更多平整地面）。这是设计意图（形制不同、占地不同），但会让大形制在崎岖地形上更难落地——与"确定性偏好"叠加后，崎岖地块可能长期只能选到 cottage。
