# 通行量驱动的道路升级（第一轮：量）设计

更新日期：2026-09-27。**本轮范围已与用户确认：拆成两轮，先量再决定；加宽留下一轮。**

依据：GAME_DESIGN.md 第 7 节「道路连接住房、仓库、农田、工坊、资源点和桥头。**先有安全通行路线，再根据频率与搬运耗时铺装和升级**。建议通行净宽：初期步道 2 格，普通道路 3 格，成熟主街 5 格」；CURRENT_STATUS 交通剩余第 1 项。

## 0. 这份文档只覆盖第一轮

用户明确的切分：

| 轮次 | 内容 |
| --- | --- |
| **本轮（第一轮）** | 采样通行量、持久化计数、纯判据、**把结果显示出来** |
| 下一轮 | **真的加宽**（2 → 3 → 5） |

**为什么必须先分**：见 §5 的两个硬点——阈值没有数据就定不出来，而加宽会撞上既有计划模型。

## 1. 现状（已核对）

- 道路**已经是 2 格宽**：`TransportCoordinator` 用 `List.of(foot, foot.relative(side))` 铺两条车道，材质 `OAK_PLANKS`，相位 `SURFACE`，规则 `ROAD_GROUND`。正好对上 GAME_DESIGN 的"初期步道 2 格"。
- `TransportPlan` 有 `Kind`（`ROAD` / `WOOD_BRIDGE`）、`Phase`、`Material`、`Rule`；进度是"步列表 + `completedSteps` 游标"。
- **全仓没有道路宽度或通行量的概念**。`width` 只出现在 `TrafficDecision` 里，那是桥梁跨度。
- **已完成的道路计划是留存的**：`TransportSavedData.MAX_COMPLETED_ROADS = 32`，所以计数有现成的家。

## 2. 采样

- 每 N tick 遍历已加载居民（`ResidentWorkLookup.loaded`，第五十三轮已有），取其**脚下的方块**（`blockPosition().below()`），在"铺面方块 → 计划 id"表里查；命中即给那条路计数。
- 该表由**已完成 `ROAD` 计划的 `SURFACE` 步**织出；计划集变化时重建（缓存 + 版本号，仿既有的 `BedCensus` 快照做法）。
- **采样节拍是判据的一部分**：阈值以"采样次数"计，所以节拍常量要与阈值写在相邻处并注明关系，否则调一个忘另一个。

## 3. 计数持久化

计在 `TransportSavedData`（`Codec.unboundedMap(Codec.STRING, Codec.INT)`，`optionalFieldOf`、**不升 schema 版本**）：键是计划 id，值是采样命中次数。

**为什么持久化而不是放在内存里**：通行量是历史量。频繁重载的存档里，内存计数永远攒不够，路就永远不会被判定为繁忙——那不是"没被使用过"，是"没被记住"。

**键的生命周期**：计划被 `MAX_COMPLETED_ROADS` 挤掉时，对应键也要清，否则映射无界增长。加载与增删计划时都要顺手清理。

## 4. 判据（纯层，有完整覆盖）

```java
public final class RoadUpgradeRules {
    /** 道路经过的档位：步道 2 → 普通 3 → 成熟主街 5（GAME_DESIGN §7 的净宽建议）。 */
    public static int nextLanes(int lanes)

    /** 这条路的通行量是否已值得加宽。 */
    public static boolean shouldUpgrade(int lanes, int traffic)
}
```

- `nextLanes`：2 → 3 → 5，到 5 不再变（返回自身）。
- `shouldUpgrade`：已满档（5）永远为假；否则 `traffic >= 阈值 * (lanes - 1)` 之类的**单调**判据（档位越高要求越多），具体形状已定死并写进检查（见 §9）。
- **阈值是发明值**：文档只给档位、不给数字。写成具名常量，注释里**标明没有依据、必须在看过真实数据后调**——不假装有出处（与第四十八轮职业名额、第五十一轮自卫数值同样的处理）。

## 5. 为什么加宽留下一轮（两个硬点，已核对）

**① 阈值无法先定。** §7 说"根据频率"，而频率要看过才知道。本轮先把数字量出来，下一轮才有依据定阈值——这也正是用户提出"先量再决定"的原因。

**② 加宽会撞上既有计划模型。**
- 计划的进度是"步列表 + 游标"。往路的**中间**插入新车道会让游标错位——这是 HOUSING 两轴升级链当初遇到过并靠"进度由世界推导"解决掉的同一类问题。
- 从既有步列表**推导不出路线方向**，因此算不出"旁边的车道"在哪。加宽要么给计划补存路线，要么另建一条只含新车道的计划。
- 再加宽还有两个次生问题：**加宽后旧车道的样本算谁的**（否则旧计划会立刻再次满足条件，形成加宽循环）；以及**加宽本身要占材料与工人**，要走既有的单在途与材料门禁。

这些合起来足够独立一轮，塞进本轮会让"量"这件事也做不干净。

## 6. 显示

`goblinsettlement status` 增加一行：各条道路的**采样计数**与**是否已达加宽条件**。

理由：GAME_DESIGN 第 151 行要求状态可读；而本轮的价值本来就有一半在"把数据摊开给人看"，否则调阈值仍是盲调。

## 7. 验证

- 新增 `RoadUpgradeRulesCheck`：档位推进（2→3→5→5 不再变）、阈值边界（刚好到、差一）、满档永不升级。
- 完整离线构建 + 全部独立检查（已达成：15 项）。
- **采样、计数持久化、显示三样都不可纯测**——只有编译与代码审查。日志与状态里必须写明。

## 8. 风险

- **阈值是发明值**：见 §4。本轮刻意不做加宽，正是为了让下一轮能拿真实数字定它。
- **采样成本**：每 N tick 遍历已加载居民（上限 64）并查表。节拍不能太密；实现时把常量与理由写在一起。
- **"脚下是铺面"不等于"在走路"**：站岗、避难、打架的居民也会被计到。本轮不区分，这是**近似的频率**，不是精确流量；若下一轮发现噪声太大，再按 `workStage` 过滤。
- **映射随计划增删的无界增长**：见 §3 的清理要求。
- **两轮之间状态不对称**：本轮结束后，路会被判定为"该加宽"但**不会真的加宽**。状态文档里要写明这个中间态，避免被读成功能已完整。

## 9. 第一轮落地结果（实现后补记）

- `planning/transport/RoadUpgradeRules`：`LADDER = {2, 3, 5}`；`nextLanes` 取梯子上第一个大于当前宽度的档，**没有更大的档时返回 5**（所以 1 → 2、4 → 5、9 → 5）；`shouldUpgrade(lanes, traffic)` 为 `lanes <= 0` 或 `lanes >= 5` 时为假，否则 `traffic >= TRAFFIC_PER_LANE * max(1, lanes - 1)`——"至少一整份"这个下限让 1 车道的路也要 200 次命中，而不是 0 次。
- **两个发明值**：`TRAFFIC_PER_LANE = 200`、`TrafficSampler.SAMPLE_INTERVAL_TICKS = 100`（5 秒一采样）。两者互相引用并写明**没有依据、必须在看过真实计数后一起重定**——命中数是按次累计的，所以采样节拍本身就是判据的一半。
- **一处实现期修正（已更正的实现细节，非遗留风险）**：`TrafficSampler` 的缓存记录原先持有对自身弱键的强引用（`owner` 字段），使键永远无法被回收；经一轮评审、按人类伙伴的指示删除了 `owner` 字段。
- `BUILT_ROAD_LANES = 2` 是"全部建成道路当前宽度"的唯一出处；`TransportCoordinator.startRoad` 的取车道循环只加了一行指向它的注释。加宽轮次会把这个常量换成按路实测的宽度。
- 计数键是计划 id、值是**命中次数**（一次采样里一名居民站在该路的一格上记 1 次）。`TransportSavedData` 用 `optionalFieldOf("traffic", Map.of())` 落盘，**未升 schema 版本**；`pruneTraffic` 在构造（读档）与 `replace`（含 `MAX_COMPLETED_ROADS` 淘汰）两处清掉没有对应计划的键。
- **计数是累计量、不按经过的采样数归一**：一条路建得越早、存在越久，它的数就越大。第二轮定阈值时必须把这一点算进去（要么接受"先建的先加宽"，要么改成按单位时间归一）。
- 显示：`goblinsettlement status` 多一行 `Road traffic: …`，按命中数降序、并列按 id 升序，最多列 8 条，达加宽条件的带 `*`。
- **本轮不加宽**：路会被判为"够格"但宽度不变。这是与用户约定好的中间态，**不要读成功能已完整**。
