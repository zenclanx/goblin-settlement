# 哥布林住宅升级链：设计

记录日期：2026-09-27
状态：设计稿，已由用户确认方向。数值为**建议初值**。

本设计落实 [GAME_DESIGN.md](GAME_DESIGN.md) 第 7 节的住宅要求（五级序列、"容量升级与品质升级分开"）与第 11 节的"公告牌显示住房空位"，并遵循 [TECH_DESIGN.md](TECH_DESIGN.md) 第 2 节的模块边界。当前进展见 [CURRENT_STATUS.md](CURRENT_STATUS.md)。

## 1. 背景：五级几何已存在，但容量既不落地也不参与判定

调查结论（证据见 `housing/` 各文件）：

- `HousingCoordinator` 已有五级几何（`blueprints()`），全部为橡木木板，每一级建在前几级之上，是一条**累积的梯子**。
- **"容量"在代码里不存在。** 全仓没有任何"这栋房子能住几人"的数据；唯一的容量是**世界里的合法床头数**，由 `BedProvisioningCoordinator` 与 `FamilyCoordinator` **各自独立扫描**得到。代码注释把容量定义为床位，但`Home` 记录里没有容量字段，居民也没有"住在哪栋房子"的关联。
- **现有几何与容量脱节**：第 3、4 级（屋顶脊梁、檐梁加地面条）**一块居住空间都不加、一张床都不加**，纯装饰。
- **升级是无条件的**：`advance()` 的通过条件只有"该格是空气 + 仓库木板超过保留量 + 有空闲工人 + 权限允许"。人口、床位、拥挤度、品质一概不参与。
- `SettlementDemand.Priority` 没有住房档；`/goblinsettlement status` 不显示任何住房信息。

设计的关键要求是**"容量升级与品质升级分开"**，以及"人口满额以后，住宅仍可以变漂亮，**不会因为房子升级又突破人口上限**"。

## 2. 两条轴

### 2.1 容量轴（决定这栋房子能容纳几张床）

| 级 | 几何（既有） | 可容纳床位 |
| --- | --- | --- |
| 0 棚 | 四角柱 + 3×3 平顶 | 1 |
| 1 木屋 | 四壁 + 门洞 + 5×5 屋顶 | 2 |
| 2 扩建 | 加侧屋 | 3 |

把"四壁与门"归入容量轴而非品质轴的理由：没有墙的棚不算住所，有了墙才真正能住人、才谈得上住几人。这样每一级容量都有实质增益，容量轴同时表达"能不能住"与"能住几人"。

### 2.2 品质轴（纯装饰，**不增加任何容量**）

| 级 | 几何（既有） |
| --- | --- |
| 0 素 | 无附加 |
| 1 优质 | 屋顶脊梁 |
| 2 成熟 | 檐梁 + 门前地面条 |

**核心不变量**：品质轴的任何一级都不改变床位数量。这是"人口满额后房子变漂亮但不突破人口上限"在代码里的落点。

### 2.3 两轴独立推进

一栋房子同时有容量目标与品质目标，两者各有各的进度。**建什么 = 容量轴 0..capacityTarget 的各步，接上品质轴 0..qualityTarget 的各步。**

## 3. 数据模型

`HousingSavedData.Home` 从单轴 `stage` 改为两条轴的目标值：

```text
Home(bed, variant, capacityTarget, qualityTarget, workerId)
```

- `bed` / `variant` / `workerId` 语义不变（`variant` 仍是朝向镜像 0..2）。
- `capacityTarget` ∈ [0,2]、`qualityTarget` ∈ [0,2]。
- **原有的 `step` 字段取消。**

### 3.1 进度由世界推导，不保存构建游标

原来用一个 `step` 整数记录"建到第几步"。两轴之后这个游标会失效：若品质步已经建好、之后容量目标又提高，新出现的容量步会落在旧游标**之前**，单纯"游标 +1"就会跳过它们、甚至重复扣料。

因此**不保存游标**。每次评估一栋房子时：把当前两轴目标合成出步骤列表，**从头逐格检查，跳过所有已经是对应方块的步骤**，第一个还没建的格就是本次要建的。既有 `advance` 里本来就有"该格已是橡木木板就前进"的逻辑，顺着它做即可。

这样目标怎么变都不会漏建或重复扣料——**正确性由构造保证，而不是靠维护一个整数**。列表只有十几到二十几步，每次全扫的开销可以忽略。

### 3.2 旧存档迁移

新增的两轴字段一律 `optionalFieldOf`。**不提升 schema 版本。**

codec 同时保留读取旧的 `stage` 与 `step` 两个可选字段，且**仅用于迁移**：加载时把旧 `stage` 映射成两轴，旧的 `step` 直接丢弃（进度改由世界推导，见 3.1）。

| 旧 stage | 容量目标 | 品质目标 |
| --- | --- | --- |
| 0 / 1 / 2 | 0 / 1 / 2 | 0 |
| 3 | 2 | 1 |
| 4 | 2 | 2 |
| **5** | **2** | **2** |

**stage 5 必须一并处理**：旧的 `advance()` 在第 4 级建完后会无条件 `stage + 1`，而 `Home` 的校验上限是 5，所以 **stage 5 是旧存档里真实可达的状态**。它在几何上与第 4 级完全相同，映射为 (2,2)。

即旧存档里已经建到第 3、4、5 级的房子，其"脊梁/檐梁"被解释成品质级而非新的一级容量。旧存档必须能读，不得因字段变化而加载失败。

## 4. 决策规则（谁决定扩建还是提品质）

纯规则函数 `HousingRules.decide`，输入"聚落的床位总数、已占人口名额、这栋房子当前的两轴值、**这栋房子周围已用的床位数**（`HousingRules.bedsNear`，以该房锚点床为中心、`BIND_RADIUS` 半径内）"，输出"扩容量 / 提品质 / 不动"：

- **床位 < 已占人口名额 + 1**（村子的床不够了）：
  - 这栋房子**还能多放一张床**（`canGainCapacity(周围已用床数, 容量目标)`）→ **扩容量**
  - **否则 → 不动**
- **否则**（床够用）：品质目标未到顶 → **提品质**；到顶 → **不动**

即：**先保证住得下，再考虑住得好。**

### 4.1 为什么缺床时饱和的房子"不动"而不是"提品质"（2026-09-27 修订）

容量只在这栋房子 BIND_RADIUS 内兑现成床（第 6 节），所以「周围已用床数已经不小于提高一级目标能提供的容量」的房子，**抬高目标只会花掉一整套容量阶段的木板（约 81 块）却仍然放不下新床**——正是本次要堵掉的白花。

`canGainCapacity` 已经是 `HousingCoordinator.hasCapacityGain`（扩地闸）与 `BedProvisioningCoordinator`（放床绑定）共用的判据；让 `decide` 也走它，"还能不能扩容"在三条路径上只有一个答案。`capacityTarget < MAX_CAPACITY_TARGET` 那半句由 `canGainCapacity` 涵盖，不再单独判，避免两处判据。

**与旧断言的冲突及取舍**：实现期 `HousingRulesCheck` 断言过"缺床且容量到顶时转提品质"（用例名 "turns to quality instead of stalling"），而本节更早的正文写着"缺房时不会去给房子加装饰"——两句不能同时成立。**现以本节为准：缺床期间不装修，装修要等床位缺口消失。** 该断言已一并改为期望"不动"。

**正向副作用**：饱和房子返回"不动"后不再占用 `HousingCoordinator` 每 40 tick 一次的决策名额（该循环取第一栋产生动作的房子就返回），能真正扩容的房子更早轮到自己；此前它要先耗掉饱和房子提品质的那几次。

**逃生路径不变**：全聚落无处可扩容时 `hasCapacityGain` 为假 → 扩地放行（6a）+ 自由放床（6.3），缺口仍能解除。

## 5. 需求档与互斥

`SettlementDemand.Priority` 新增 **`HOUSING`**，插在 `TRANSPORT` 与 `CONSTRUCTION` 之间。对照设计第 3 节的默认优先级："关键交通和设施维修 → **必要住房** → 扩张工程"。

效果：**缺房时扩地自动让位**（`ExpansionCoordinator` 以 `priority() == READY` 为闸），与交通档的互斥方式完全一致，继续保证"同时只推进一项工程"。**但有一个例外，见 6a**——当没有任何房子还能通过提高容量吸收缺口时，扩地必须放行，否则会死锁。

`HOUSING` 的判定依据是**床位缺口**（床位 < 已占名额 + 1），与第 4 节的规则同源，避免两套判据。床位是世界方块，而 `SettlementDemand.assess` 是纯函数，所以这个布尔量由**调用方**算好传入——与既有的 `trafficPending` 参数完全同构。

## 6. 床位与房屋的绑定

这是本设计对既有行为的**唯一一处真实改变**。

现状：`BedProvisioningCoordinator` 在村里**任意位置**放床，只维持"床数 ≥ 已占名额 + 1"。

改为：**放新床时，该位置必须落在某栋容量尚未用满的房子附近**。

### 6.1 绑定半径必须是 8，不能是 4

以房子的锚点床为中心，绑定半径取 **8 格（Chebyshev x/z ≤ 8、|dy| ≤ 4）**。

**不能用 4**：锚点床自己就落在"4 格内已有床则排除"的互斥区里，绑定半径若同为 4，两个区域同中心、交集为空——第二张床在数学上永远放不出来。半径 8 之下，第二、三张床可以落在距锚点 5～8 格处，即在互斥区之外。

### 6.2 容量按**已建成**的几何算，不按目标算

一栋房子已建成的容量 = 1（锚点床）+ 已经真正铺完的容量阶段数。**只把目标调高、几何还没建起来时，不算容量**——否则一提高目标就允许放床，容量落地就落空了，正好退回设计第 1 节批评的现状。

### 6.3 逃生口：没有任何房子有容量空位时，回到自由放床

当所有房子的容量都已用满（或一栋房子都没有）时，**绑定不启用**，恢复旧行为：在任意合法位置放床。

这不是可选的便利，而是**必须的**——否则会死锁：

- **初始营地**：`CampGenerationCoordinator` 在营地布局阶段**直接放置** 8 张床，完全不走本协调器，绑定规则管不到它们。而管理员的 `found` 若一床没有，此时 homes 为空，也必须允许放第 1 张床。
- **营地第 9 张床**：营地 8 张床由营地生成直接放置、间距只有 2 格。注册成 home 时会先过一道"与已有 home 的床相距足够远"的检查（同层 7×7 窗口），**营地这 8 张床彼此太近，所以一栋都不会注册**——不是"注册成一栋"。于是 `homes` 为空、逃生口的"没有房子"分支生效、绑定不启用。同时地块 1 已被 4 格互斥饱和（现状就有的性质），第 9 张床本来就放不进地块 1。若严格绑定，第 9 张床无处可放、缺口永不解除。

  **更正说明**：本节早先写的是"这 8 张床只会注册成 1 个 home，那栋房子恒无空位"。那是错的——注册检查比它严格，实际是**零栋**注册，逃生口走的是"没有房子"分支而非"有房子但没空位"分支。两种情形下**结论与实现都相同**（绑定不启用、扩地例外必须存在），但机制以本段为准。

数量闸门（`床数 < 已占名额 + 1`）**不因逃生口而放宽**：逃生口只放宽**位置**，不放开**数量**。

## 6a. 扩地闸门的例外

第 5 节说"缺房时扩地让位"。但结合 6.3 的死锁链，还需要一个例外：

**当没有任何房子还能通过提高容量吸收缺口时，扩地照常放行。**

即扩地闸门为：`优先级 == READY`，**或**（`优先级 == HOUSING` **且** 没有任何房子还有容量可长）。

这是营地与"容量饱和"场景唯一的解除路径：营地没有可长的房子（且如上所述一栋 home 都没有）→ 扩地 → 新地块有地方放床 → 第 9 张床落地 → 被注册成新 home → 短缺解除。

## 10. 风险

- **改存档结构**：`Home` 的字段从 `stage` 变为两条轴。必须保证旧存档能读；实现时以"旧存档加载后两轴值符合第 3.2 节的映射表"为验收点。
- **床位绑定的连带影响**：`FamilyCoordinator` 现在直接数世界里的床。床位一旦受房屋容量约束，"床不够"的成因可能从"还没放床"变成"房子容量不够"，而后者要靠建造解决、可能更慢。需要在实现时确认生育判定不会因此长期卡死，并在文档里说明这一变化。
- **绑定的残余死角**：若某栋房子有空位、但它周围恰好被别的床的互斥区铺满，则放不出床；此时若它同时又是"还能长容量"的，扩地仍会被挡。条件很苛刻（需要"有空位"与"周围 9×9 全被床占满"同时成立），本轮不做额外缓解，记录在案。**与 4.1 的关系**：这种房子会被 `decide` 判为"还能扩容"而反复扩容量（容量轴上限 2 级，所以有界），却始终放不下床——与 4.1 堵掉的"白花"同源，但成因是物理放床受阻而非容量算式算错，本轮仍不缓解。
- **附近床数会重复计数**：半径 8 的统计会跨房子重复计入同一张床（两栋房子可相距 7 格）。营地那种密集布局下，唯一那栋房子的"附近床数"会长期高估、从而长期走逃生口。可接受（营地本就是宿舍式布局），但意味着**绑定只在稀疏、正常的聚落布局里真正生效**。
- **`new Home(bed, variant, 0, 0)` 的文本不变而语义改变**：旧代码里那两个 0 是 `stage`/`step`，新代码里是两条轴的目标。升级路径正确，但审查时容易误读，提交说明里要写明。
- **进度推导的正确性**：游标取消后，进度完全由"哪些格已经是正确方块"推导。风险转移到"合成出的步骤列表与目标不一致"——例如两轴目标越界、或合成顺序不稳定导致同一步骤时有时无。必须有覆盖"目标变化后不重复扣料、不漏建"与"同一组目标每次合成出同一份列表"的检查。
- **互斥链再加一环**：`HOUSING` 档会让扩地在缺房时让位。若住房长期无法满足（材料不足等），扩地会被一直挡住——与交通档同类的风险，需要确认缺口有解除路径。
