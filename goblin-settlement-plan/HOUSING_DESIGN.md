# 哥布林住宅升级链：设计

记录日期：2026-09-27
状态：设计稿，已由用户确认方向。数值为**建议初值**。

本设计落实 [GAME_DESIGN.md](GAME_DESIGN.md) 第 7 节的住宅要求（五级序列、"容量升级与品质升级分开"）与第 11 节的"公告牌显示住房空位"，并遵循 [TECH_DESIGN.md](TECH_DESIGN.md) 第 2 节的模块边界。当前进展见 [CURRENT_STATUS.md](CURRENT_STATUS.md)。

## 1. 背景：五级几何已存在，但容量既不落地也不参与判定

调查结论（证据见 `housing/` 各文件）：

- `HousingCoordinator` 已有五级几何（`blueprints()`），全部为橡木木板，每一级建在前几级之上，是一条**累积的梯子**。
- **"容量"在代码里不存在。** 全仓没有任何"这栋房子能住几人"的数据；唯一的容量是**世界里的合法床头数**，由 `BedProvisioningCoordinator` 与 `FamilyCoordinator` **各自独立扫描**得到。代码注释把容量定义为床位，但`Home` 记录里没有容量字段，居民也没有"住在哪栋房子"的关联。
- **现有几何与容量脱节**：第 3、4 级（屋顶脊梁、檐梁加地面条）**一块居住空间都不加、一张床都不加**，纯装饰。
- **升级是无条件的**：`advance()` 的通过条件只有"该格是空气 + 仓库木板超过保留量 + 有空闲工人 + 权限允许"。人口、床位、拥挤度、品质一概不参与。
- `SettlementDemand.Priority` 没有住房档；`/goblinsettlement status` 不显示任何住房信息。

设计的关键要求是**"容量升级与品质升级分开"**，以及"人口满额以后，住宅仍可以变漂亮，**不会因为房子升级又突破人口上限**"。

## 2. 两条轴

### 2.1 容量轴（决定这栋房子能容纳几张床）

| 级 | 几何（既有） | 可容纳床位 |
| --- | --- | --- |
| 0 棚 | 四角柱 + 3×3 平顶 | 1 |
| 1 木屋 | 四壁 + 门洞 + 5×5 屋顶 | 2 |
| 2 扩建 | 加侧屋 | 3 |

把"四壁与门"归入容量轴而非品质轴的理由：没有墙的棚不算住所，有了墙才真正能住人、才谈得上住几人。这样每一级容量都有实质增益，容量轴同时表达"能不能住"与"能住几人"。

### 2.2 品质轴（纯装饰，**不增加任何容量**）

| 级 | 几何（既有） |
| --- | --- |
| 0 素 | 无附加 |
| 1 优质 | 屋顶脊梁 |
| 2 成熟 | 檐梁 + 门前地面条 |

**核心不变量**：品质轴的任何一级都不改变床位数量。这是"人口满额后房子变漂亮但不突破人口上限"在代码里的落点。

### 2.3 两轴独立推进

一栋房子同时有容量目标与品质目标，两者各有各的进度。**建什么 = 容量轴 0..capacityTarget 的各步，接上品质轴 0..qualityTarget 的各步。**

## 3. 数据模型

`HousingSavedData.Home` 从单轴 `stage` 改为两条轴的目标值：

```text
Home(bed, variant, capacityTarget, qualityTarget, workerId)
```

- `bed` / `variant` / `workerId` 语义不变（`variant` 仍是朝向镜像 0..2）。
- `capacityTarget` ∈ [0,2]、`qualityTarget` ∈ [0,2]。
- **原有的 `step` 字段取消。**

### 3.1 进度由世界推导，不保存构建游标

原来用一个 `step` 整数记录"建到第几步"。两轴之后这个游标会失效：若品质步已经建好、之后容量目标又提高，新出现的容量步会落在旧游标**之前**，单纯"游标 +1"就会跳过它们、甚至重复扣料。

因此**不保存游标**。每次评估一栋房子时：把当前两轴目标合成出步骤列表，**从头逐格检查，跳过所有已经是对应方块的步骤**，第一个还没建的格就是本次要建的。既有 `advance` 里本来就有"该格已是橡木木板就前进"的逻辑，顺着它做即可。

这样目标怎么变都不会漏建或重复扣料——**正确性由构造保证，而不是靠维护一个整数**。列表只有十几到二十几步，每次全扫的开销可以忽略。

### 3.2 旧存档迁移

新增的两轴字段一律 `optionalFieldOf`。**不提升 schema 版本。**

codec 同时保留读取旧的 `stage` 与 `step` 两个可选字段，且**仅用于迁移**：加载时把旧 `stage` 映射成两轴，旧的 `step` 直接丢弃（进度改由世界推导，见 3.1）。

| 旧 stage | 容量目标 | 品质目标 |
| --- | --- | --- |
| 0 / 1 / 2 | 0 / 1 / 2 | 0 |
| 3 | 2 | 1 |
| 4 | 2 | 2 |

即旧存档里已经建到第 3、4 级的房子，其"脊梁/檐梁"被解释成品质级而非新的一级容量。旧存档必须能读，不得因字段变化而加载失败。

## 4. 决策规则（谁决定扩建还是提品质）

新增纯规则函数，输入"聚落的床位总数、已占人口名额、这栋房子当前的两轴值"，输出"扩容量 / 提品质 / 不动"：

- **床位 < 已占人口名额 + 1**（村子的床不够了）→ **扩容量**
- **否则**（床够用）→ **提品质**

即：**先保证住得下，再考虑住得好。** 缺房时不会去给房子加装饰；床够用时也不会无谓地扩建。

品质目标只在容量目标已达上限、或当前人口规模下不再需要更多容量时才推进。

## 5. 需求档与互斥

`SettlementDemand.Priority` 新增 **`HOUSING`**，插在 `TRANSPORT` 与 `CONSTRUCTION` 之间。对照设计第 3 节的默认优先级："关键交通和设施维修 → **必要住房** → 扩张工程"。

效果：**缺房时扩地自动让位**（`ExpansionCoordinator` 以 `priority() == READY` 为闸），与交通档的互斥方式完全一致，继续保证"同时只推进一项工程"。

`HOUSING` 的判定依据是**床位缺口**（床位 < 已占名额 + 1），与第 4 节的规则同源，避免两套判据。

## 6. 床位与房屋的绑定

这是本设计对既有行为的**唯一一处真实改变**。

现状：`BedProvisioningCoordinator` 在村里**任意位置**放床，只维持"床数 ≥ 已占名额 + 1"。

改为：**放新床时，该位置必须落在某栋容量尚未用满的房子附近**（以该房子的床坐标为锚点，复用既有的"4 格内不重复放床"那套距离逻辑）。房子的容量已满，就不再在其周围放床。

于是**床位增长必须靠先扩建房子**——容量线由此真正接通，"一栋房子能住几人"从数据变成了世界里的实际约束。

## 7. 显示

`/goblinsettlement status` 增加一行：床位数 / 已占人口名额 / 空位。

**实体公告牌方块不在本轮**：设计第 11 节要求的是一个显示这些信息的方块，目前工程里没有该方块，属于独立的功能，留待后续。

## 8. 验证

- 两轴步骤合成、游标跳过已建步骤、决策规则、旧存档映射，这几块都是纯逻辑，按项目既有写法各写独立检查（无 JUnit、`main` + `require`、成功打印 `XxxCheck passed`，注册进 `check` 聚合），先写失败再实现。
- `SettlementDemandCheck` 增加 `HOUSING` 档用例。
- 完整离线构建 + 全部独立检查通过。
- **不做游戏内验证**：按用户约定，初版代码全部完成后才统一测试。

## 9. 范围外（本轮不做）

- **蓝图与材料清单迁到受校验的数据文件**（TECH_DESIGN 第 6 节要求：资源标识存在、升级链无环、蓝图有合法入口、数值不越界）。本轮几何仍硬编码在 `HousingCoordinator` 里。
- **改建安全**：设计第 7 节要求"改建前确认材料和临时住处，避免拆掉唯一住房"。本轮不做拆除，只做增量建造，所以该风险暂不成立。
- **公共设施**（仓库、农田、工坊、厨房、巡逻点、广场、交易摊位）。
- **更多蓝图**：`Home.variant` 仍是朝向镜像，不是可选形制。
- **实体公告牌方块**。
- **住户分配**：居民不绑定到具体房子（用户已明确选择）。
- **历史保留**（旧仓库与营火被赋予历史感）。

## 10. 风险

- **改存档结构**：`Home` 的字段从 `stage` 变为两条轴。必须保证旧存档能读；实现时以"旧存档加载后两轴值符合第 3.2 节的映射表"为验收点。
- **床位绑定的连带影响**：`FamilyCoordinator` 现在直接数世界里的床。床位一旦受房屋容量约束，"床不够"的成因可能从"还没放床"变成"房子容量不够"，而后者要靠建造解决、可能更慢。需要在实现时确认生育判定不会因此长期卡死，并在文档里说明这一变化。
- **进度推导的正确性**：游标取消后，进度完全由"哪些格已经是正确方块"推导。风险转移到"合成出的步骤列表与目标不一致"——例如两轴目标越界、或合成顺序不稳定导致同一步骤时有时无。必须有覆盖"目标变化后不重复扣料、不漏建"与"同一组目标每次合成出同一份列表"的检查。
- **互斥链再加一环**：`HOUSING` 档会让扩地在缺房时让位。若住房长期无法满足（材料不足等），扩地会被一直挡住——与交通档同类的风险，需要确认缺口有解除路径。
