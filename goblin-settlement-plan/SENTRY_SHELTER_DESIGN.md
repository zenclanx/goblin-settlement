# 哨卫引导避难设计

更新日期：2026-09-27。依据：GAME_DESIGN.md 第 30 行（哨卫职责含引导避难）、第 132 行（「哨卫报警，**非战斗居民与儿童避难**」）、第 151 行（居民简短状态展示正在做什么）；PROFESSION_DESIGN.md §12；SENTRY_PATROL/ALERT/DEFENCE_DESIGN.md（哨卫的前三项职责）。

## 1. 目标与范围

**目标**：建立**聚落级警戒状态**，警报期间非战斗居民与儿童中断工作、前往最近的已建成房屋躲避；警报解除后原地恢复工作。哨卫的"引导"落在**守位**——它站到威胁与村子之间，而不是挨家挨户带路。

**本轮做**：持久化警戒状态、避难所选择（纯规则 + 检查）、居民的避难行为、巡逻哨卫的守位。

**本轮不做**：
- **逐户护送**（让哨卫走到居民身边再带他们走）：需要跟随/带队 AI 与两者导航的互锁，体量与风险都明显更大。用户已明确否掉。
- 避难所的**容量与出入判定**：几个居民挤同一间小屋、甚至被挤出墙外，本轮不管。
- 儿童专属行为（跑得更慢、哭喊之类）：儿童只是"职业为 `UNASSIGNED` 因而自动纳入避难"。
- 新方块/设施：GAME_DESIGN 的待建设施清单里**没有避难所**，本轮不造。

## 2. 警戒状态（持久化）

`DefenseSavedData` 加两个字段：

| 字段 | 含义 |
| --- | --- |
| `alertTicks`（int） | 警戒**剩余** tick 数，归零即解除 |
| `lastThreat`（`Optional<BlockPos>`） | 最近报告到的威胁位置，供哨卫守位 |

**不升 schema 版本**：两个都用 `optionalFieldOf` 并给默认值（`0` 与空），旧存档照常读入——与 `HousingSavedData` 加 `style` 时同样的做法。（`schema_version` 是 `fieldOf` 必填项，旧档本来就带。）

**为什么持久化而不是瞬态**：跨存档重载的袭击应当继续让人躲着。

**为什么存剩余 tick 而不是解除时刻**：存绝对时刻的话，玩家把该维度时间倒退（新世界、`/time set`）会让判定长期为真、**居民永久避难**。存剩余 tick 由协调器每 tick 递减，就只与"经过了多少时间"有关，与绝对时间无关。

**置位与续期**：`DefenseCoordinator` 一处负责——
- `onResidentAttack`（有人挨打）置位；
- `reportSighting` **真的惊动了傀儡**时置位；
- 每次置位都把剩余 tick 刷成 15 秒。**沿用傀儡既有的 `ALERT_TICKS`（`20 * 15`）节奏**：还有目击或挨打就持续续期，安静 15 秒才解除。

## 3. 谁去避难、去哪

- **避难者 = 职业不是 `SENTRY` 的居民**。儿童在名册里是 `UNASSIGNED`，因此**自动纳入**——正好对应 GAME_DESIGN 的"非战斗居民与儿童"。哨卫不躲。
- **避难所 = 已登记房屋的锚点床位置**（`HousingSavedData.homes`）。语义对（有墙有门）、数据现成、不需要新方块。
- **选择规则是纯函数**：`ShelterRules.nearest(List<int[]> shelters, int[] from) -> int`，取最近者、并列按 x 再按 z（与 `PatrolRules` 同风格），**无避难所时返回 -1**。这是本轮唯一能被独立检查覆盖的部分。

## 4. 避难行为

居民加**独立的 `sheltering` 状态**，**不改 `workStage`**：

- 好处是警报解除后**工作原地恢复**，不需要保存/还原被中断的工作；
- 代价是"正在搬运的居民会带着材料去躲"——可以接受（材料没丢）。

在 `customServerAiStep` 里、**工作推进之前**判断（与第五十一轮的自卫守卫同构，都是"某状态下让出导航"）：

- 处于警戒且自己不是哨卫 → 中断工作，前往避难所，到了就停在那里；
- 警戒解除 → 清状态、回去干活；
- **结算不到避难所**（一栋房子都没有）→ 不避难，照常干活（总得有人干活，且无处可去时乱跑更糟）。

`waitReason` 写"避难中"，让 `/goblinsettlement work` 看得见（GAME_DESIGN 第 151 行）。

## 5. 哨卫的"守位"

警戒期间，**正在巡逻的那名哨卫**不再走航点，而是**朝 `lastThreat` 移动并守住**，警报解除后回到巡逻。这就是"引导"的落点：它站在威胁与村子之间。

实现上落在 `tickPatrolWork` 里：先照旧 `reportSighting`（这一条让警戒在它持续看见威胁时不断续期），再看警戒——有警戒且有威胁位置就走守位逻辑，否则走原来的航点逻辑。**不新增寻敌**：它守的是"最后被报告到的位置"，不是自己搜出来的目标。

## 6. 验证

**本轮有新增独立检查**（打破第四十七、五十、五十一轮连续三轮无新覆盖的局面）：

- 新增 `ShelterRulesCheck` 与 `shelterRulesCheck` 任务：最近者胜出、并列按 x 再按 z、同坐标去重不需要（避难所来自房屋集合，天然唯一，但仍要覆盖空列表返回 -1）、单一避难所、确定性（同输入两次同结果）。

**但这只覆盖选择规则**：避难行为本身（真的中断工作、真的走过去、解除后真的回去）与哨卫守位**仍不可纯测**，只有编译与代码审查。日志与状态里必须写明这个界。

完整离线构建 + 全部独立检查（届时 **14 项**）。

## 7. 风险

- **实体行为仍无自动证据**：见 §6。这是第四轮实体侧改动了，累积的未验证面又扩大一层。
- **房屋容量未考虑**。**已补（第五十三轮）**：每栋房最多容纳它**已建成的床位数**（`HousingRules.builtCapacity`，1–3）；最近者满了就让给次近，全满则**照常干活**。仍存在的边界：早期人多房少，**一定会有居民找不到避难所**；占用是**扫描得到的、不是预留的**，同 tick 两人可能选到同一间房而超员 1。见 [SENTRY_SHELTER_QUALITY_DESIGN.md](SENTRY_SHELTER_QUALITY_DESIGN.md)。
- **避难所可能是没有墙的棚**。**已补（第五十三轮）**：候选收窄为**容量轴 1 级几何已建成**（四壁 + 门洞）的房屋；`HousingCoordinator.shelterCapacity` 返回 0 即"不是避难所"。仍存在的边界：那只说明算出的几何建完了，不等于居民真能挤进去（见上一条）。
- **两个守卫的先后**：`customServerAiStep` 里现在有两个"让出导航"的守卫（自卫、避难）。哨卫不避难、非哨卫不还击，所以**实际不重叠**；但顺序仍要写清并在源码注释里说明，免得后人以为可以随便换。
- **警戒状态存"剩余 tick"而不是"解除时刻"**：若存绝对时刻，玩家把该维度时间倒退（新世界、`/time set`）会让 `alertUntilTick` 长期为真，**居民永久避难**。改为存剩余 tick、由协调器每 tick 递减，就只与"经过了多少时间"有关，与绝对时间无关。代价是它**只在有玩家加载该维度时才递减**（协调器挂在世界 tick 上），所以服务器停摆期间警戒不会自然消退——这与"区块不活动时任务暂停"的既有约定一致，可接受。
